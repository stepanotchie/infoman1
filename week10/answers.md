## Task 1 — Safe INSERT

**Approach / explanation:**
I inserted the Scientific Calculator and the Compass with `INSERT INTO products (product_name, sku, price, stock_quantity, status)`, naming every target column so each value maps to the right column and `product_id` is generated by AUTO_INCREMENT. After each insert I ran a `SELECT` filtered by the new `sku`, which returned exactly one correct row (product_id 6 and 7). For the rejected insert I used the text `'free'` as the price of a Sticky Notes product: `price` is `DECIMAL(10,2)`, so MySQL refused it with ERROR 1366 (wrong data type) instead of storing bad data, and a follow-up `SELECT COUNT(*)` returned 0, proving nothing was stored.

**Code / query used (if applicable):**
```sql
INSERT INTO products (product_name, sku, price, stock_quantity, status)

SELECT product_id, product_name, sku, price, stock_quantity, status

WHERE sku = 'CALC-SCI-001';

VALUES ('Compass', 'CMP-001', 120.00, 50, 'Active');

FROM products

-- Rejected insert (wrong data type for price)

```

**Reflection question:**
Listing target columns makes an INSERT safer because each value is tied to a named column, so values cannot silently land in the wrong column if the table's column order differs from what I assumed or changes later. ## Task 2 — UPDATE & DELETE Without Collateral Damage

**Approach / explanation:**
For both changes I followed the safe change loop: preview with a `SELECT` using the final condition, execute the UPDATE/DELETE with the same condition, then verify with another `SELECT`. I used the stable primary key (`product_id = 6` for the Calculator, `product_id = 5` for the Eraser) instead of the product name, so only one row can match. Before deleting the Eraser I also checked that it has no rows in `sales`. Without its WHERE clause, the UPDATE would have set the price of every product in the table to 875.00, and the DELETE would have tried to remove every row in `products`, emptying the table.

**Code / query used (if applicable):**
```sql
-- Update: (a) preview
SELECT product_id, product_name, price FROM products WHERE product_id = 6;

-- Update: (b) execute
UPDATE products
SET price = 875.00
WHERE product_id = 6;

-- Update: (c) verify
SELECT product_id, product_name, price FROM products WHERE product_id = 6;

-- Delete: (a) preview
SELECT product_id, product_name, sku FROM products WHERE product_id = 5;

-- Delete: check the product has no sales before deleting
SELECT COUNT(*) AS eraser_sales FROM sales WHERE product_id = 5;

-- Delete: (b) execute
DELETE FROM products
WHERE product_id = 5;

-- Delete: (c) verify
SELECT product_id, product_name, sku FROM products WHERE product_id = 5;
```

**Evidence (screenshot filename, output, or file reference in this folder):**
- `task2a_output.png` — UPDATE preview: 1 row, Scientific Calculator, price 850.00.
- `task2b_output.png` — UPDATE executed (`Rows matched: 1  Changed: 1`) and verified: price is now 875.00.
- `task2c_output.png` — DELETE preview (1 row, Eraser, ER-001), `eraser_sales` = 0, DELETE executed (1 row affected), and verify returns `Empty set`.

**Reflection question:**
Without WHERE, the UPDATE would have changed the price of all products to 875.00 (a 10.00 Eraser and a 350.00 USB Drive would cost the same as the Calculator) and the DELETE would have tried to remove every product, so the WHERE clause is the whole safety boundary. A stable identifier such as `product_id` is safer than a name because it is unique and matches exactly one row, while a descriptive name like `'Notebook'` can be shared by several variants and would change or remove all of them.

## Task 3 — Self Join & Cross Join

**Approach / explanation:**
For the self join I used the `employees` table twice with two aliases, `e` for the employee and `m` for the manager, joined on `e.manager_id = m.employee_id`. LEFT JOIN keeps Lea Ramos because she has no manager (her `manager_id` is NULL), so she stays in the result with a NULL manager cell, whereas an INNER JOIN would silently drop her. For the cross join I combined `colors` and `sizes` with `CROSS JOIN` and no ON clause, which returned all 9 pairs (3 colors × 3 sizes), confirmed by `COUNT(*)`. A genuine business use is generating every color-size variant of a notebook for the catalog; it must never be an accidental missing ON, because the rows multiply (rows in A × rows in B) and would produce thousands of meaningless pairings from real tables.

**Code / query used (if applicable):**
```sql
-- Self join with LEFT JOIN
SELECT e.employee_id, e.employee_name AS employee, m.employee_name AS manager
FROM employees AS e
LEFT JOIN employees AS m
ON e.manager_id = m.employee_id
ORDER BY e.employee_id;

-- Cross join of colors and sizes
SELECT c.color_name, s.size_name
FROM colors AS c
CROSS JOIN sizes AS s
ORDER BY c.color_name, s.size_name;

-- Cross join row count
SELECT COUNT(*) AS total_combinations
FROM colors AS c
CROSS JOIN sizes AS s;
```

**Evidence (screenshot filename, output, or file reference in this folder):**
`task3_output.png` — self join (3 rows; Lea Ramos has manager NULL, Carlo Reyes and Dana Cruz have manager Lea Ramos), cross join (9 color-size pairs), and `total_combinations` = 9.

**Reflection question:**
The self join needs two aliases because the same table plays two roles (employee and manager), and without separate names MySQL cannot tell which copy each column belongs to (it raises a "Not unique table/alias" error). It needs a LEFT JOIN because the top manager has no manager, and an inner join would remove her row. A CROSS JOIN is the deliberate choice only when I truly want every combination of two independent lists, such as colors × sizes for product variants; if the tables are related, I use an ON condition instead.

## Task 4 — Constraints & Table Evolution

**Approach / explanation:**
I first added `contact_number VARCHAR(20)` to `products` with `ALTER TABLE`. Before adding any rule I checked the existing data (no NULL names, no duplicate skus, no prices ≤ 0), because a constraint cannot repair old bad rows. Then I added the three rules with `ALTER TABLE` (`product_name NOT NULL`, `sku UNIQUE`, `CHECK (price > 0)`) and for each one ran a valid write that passed and an invalid write that the database rejected (ERROR 1048, ERROR 1062 and ERROR 3819). As an extra I also added `DEFAULT 0` on `stock_quantity` and inserted a row without it, which stored 0.
Syntax caveat: `MODIFY` replaces the whole column definition, so `VARCHAR(100)` has to be repeated when adding NOT NULL, and CHECK is only enforced on MySQL 8.0.16 or newer (older versions accept the syntax but ignore it). I tested this in my own MySQL environment by running `SELECT VERSION();` and then the invalid inserts, which were actually rejected, proving the rules are enforced rather than trusting that the `ALTER TABLE` succeeded.

**Code / query used (if applicable):**
```sql
-- Add contact_number column
ALTER TABLE products
ADD COLUMN contact_number VARCHAR(20);

-- Check existing data before adding constraints
SELECT COUNT(*) AS null_names FROM products WHERE product_name IS NULL;
SELECT sku, COUNT(*) AS copies FROM products GROUP BY sku HAVING COUNT(*) > 1;
SELECT COUNT(*) AS bad_prices FROM products WHERE price <= 0 OR price IS NULL;

-- Rule 1 — product_name NOT NULL
ALTER TABLE products
MODIFY product_name VARCHAR(100) NOT NULL;

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES ('Stapler', 'STP-001', 95.00, 40, 'Active');           -- valid write

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES (NULL, 'XXX-001', 50.00, 10, 'Active');                -- invalid write (rejected)

-- Rule 2 — sku UNIQUE
ALTER TABLE products
ADD CONSTRAINT uq_products_sku UNIQUE (sku);

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES ('Highlighter', 'HL-001', 30.00, 60, 'Active');        -- valid write

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES ('Notebook Copy', 'NB-001', 45.00, 10, 'Active');      -- invalid write (rejected)

-- Rule 3 — CHECK (price > 0)
ALTER TABLE products
ADD CONSTRAINT chk_products_price CHECK (price > 0);

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES ('Pencil Case', 'PC-001', 85.00, 25, 'Active');        -- valid write

INSERT INTO products (product_name, sku, price, stock_quantity, status)
VALUES ('Free Pen', 'FP-001', -5.00, 10, 'Active');           -- invalid write (rejected)

-- DEFAULT on stock_quantity
ALTER TABLE products
MODIFY stock_quantity INT DEFAULT 0;

INSERT INTO products (product_name, sku, price, status)
VALUES ('Paper Clips', 'PCL-001', 20.00, 'Active');

-- Syntax testing — server version
SELECT VERSION() AS mysql_version;

-- Final table contents
SELECT product_id, product_name, sku, price, stock_quantity, status, contact_number
FROM products
ORDER BY product_id;
```

**Evidence (screenshot filename, output, or file reference in this folder):**
`task4_output.txt` — full console output of every statement above. The rejected writes are:
- NOT NULL: `ERROR 1048 (23000): Column 'product_name' cannot be null`
- UNIQUE: `ERROR 1062 (23000): Duplicate entry 'NB-001' for key 'products.uq_products_sku'`
- CHECK: `ERROR 3819 (HY000): Check constraint 'chk_products_price' is violated.`

The final table shows the passing rows (Stapler, Highlighter, Pencil Case, Paper Clips with stock 0) and the new `contact_number` column (NULL for all rows).

**Reflection question:**
Constraints are checked when data is written, so they block future bad writes but never fix rows that are already stored; if old rows already break the rule, the `ALTER TABLE` is simply refused instead of cleaning them. Before adding NOT NULL I must first find and fix any existing NULL values in that column (for example with an `UPDATE` that fills in a real value, or by deleting the bad rows), otherwise the change fails.

## Task 5 — Reflection

**Approach / explanation:**
This task is a written reflection, so there is no SQL for it. I compared when a campus bookstore should rely on application-level checks versus database-level constraints, using the price and sku rules from Task 4 as the example, and described one mistake from the lab (a self join written without its ON condition, from Task 3), its symptom, and the fix.




> For a campus bookstore I would use both layers, because they do different jobs. Application-level checks, such as a form that rejects text in the price box, give cashiers fast, friendly feedback. They are not enough alone, since an import script, another app, or a manual query can bypass the form. Database constraints are the last line of defense: in Task 4, CHECK (price > 0) rejected a price of -5, and UNIQUE on sku rejected a second NB-001, no matter which program sent the INSERT. So I would keep friendly validation in the app and the non-negotiable rules (required name, unique sku, positive price) in the database. Constraints only guard future writes, so I ran clean-data checks before adding them.
>
> One mistake I made in Task 3 was writing the employee self join without its ON condition. The symptom was 9 rows instead of 3, with every employee paired with every manager, including themselves. I fixed it by adding ON e.manager_id = m.employee_id, which returned 3 rows and kept Lea with a NULL manager.

**Reflection question:**
I would trust the application form for fast, friendly feedback (for example, telling a cashier a price must be a number) and the database constraint for any rule that must never be broken, such as a unique `sku` or `price > 0`, since the database is the only layer every program must pass through. The single symptom that tells me the wrong layer was trusted is bad data appearing in the table anyway, such as a duplicate sku or a negative price that was stored because the rule lived only in the form.
